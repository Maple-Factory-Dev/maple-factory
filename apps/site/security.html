Security

How Maple Factory handles your code and credentials.

Maple Factory has three parts: a server you deploy to your own Cloudflare account, a runner on your team’s machines, and a Mac app. This page says what each one does with sign-in, tokens, secrets and updates, for anyone reviewing it.

Server maple-server

Where it runs, and who has the data

  • Each organization runs its own factory: a Cloudflare Worker with two Durable Objects, a D1 database and an R2 bucket, deployed to your Cloudflare account with the Deploy to Cloudflare button or npx maple-factory install. There is no shared, hosted Maple Factory service.
  • Tasks, plans, members, machines, the audit log and repo secrets are stored in that account’s D1, Durable Object storage and R2. Anyone with access to the Cloudflare account can read them.
  • The factory makes outbound requests to GitHub’s API, to maplefactory.dev’s release feed (to fetch runner builds and check for new server versions), to Slack, Linear or Jira only if you connect them, and to Sentry with error reports unless you turn them off.
  • Updates are yours to apply. A button deploy gets a daily GitHub Actions workflow that opens a pull request with the new release, which you review and merge. maple install and maple update only deploy a server release whose manifest is signed with Maple Factory’s Ed25519 release key and whose bundle matches the manifest’s SHA-256.

Sign-in

  • People sign in with GitHub, through a GitHub App your factory creates for itself at /setup. /setup only accepts an app owned by your configured organization, and changes nothing once sign-in works.
  • Only active members of that GitHub organization can sign in, plus any logins listed in GITHUB_ALLOWED_LOGINS. For a factory on a personal account, only that account and the listed logins can sign in. Refused sign-ins are recorded in the audit log.
  • Org membership is checked with GitHub at each sign-in, and again every 10 minutes for anyone with the web or Mac app open. Someone who has left the organization is cut off at the next check: their web sessions and app tokens stop working, their open terminals close, and their machines stay offline until they can sign in again. An admin can also cut someone off at once with Revoke access in the Mac app’s settings. On a personal-account factory, removing a login from the list signs them out at once.
  • The web app gets a session cookie signed with HMAC-SHA256. It is HttpOnly, SameSite=Lax, and on HTTPS Secure with a __Host- prefix. The GitHub OAuth flow uses a signed, single-browser state that expires after 10 minutes.
  • Browser requests that change data, and WebSocket upgrades, are refused unless their Origin is the factory itself.

Roles

  • GitHub organization owners are admins. An admin can make another member an admin in the factory. That changes their role, but doesn’t let in anyone who couldn’t already sign in.
  • Only admins can add or remove repos, set or delete repo secrets, change worktree scripts, the risk policy, prompts and MCP connectors, or see usage statistics.
  • Only a machine’s owner or an admin can start or end sessions on that machine, change its settings, or remove it.
  • Only a machine’s owner or an admin can open, type into or resize the live terminal of a session on that machine, unless they share that one session with chosen teammates, to watch or to type too. A watch-only teammate’s keystrokes and resizes are dropped. Sharing and unsharing are recorded in the audit log, unsharing closes the teammate’s terminal, and a share ends with the session or when that teammate’s access is revoked. Taking back someone’s admin grant closes the terminals they opened as an admin.

How the Mac app and runners authenticate

  • The Mac app signs in with GitHub’s device flow and gets a factory token (mft_…) that expires after 30 days.
  • To add a machine, a member asks for an enrollment code. It can be used once and expires after 15 minutes. The runner trades it for a machine token (mfr_…) and uses that token to connect from then on.
  • The factory stores only SHA-256 hashes of app tokens, machine tokens and enrollment codes. Tokens are 32 random bytes. Enrolling a machine again replaces its token and disconnects the old connection. Removing a machine deletes its token and disconnects it.

Repo secrets

  • Admins store per-repo secrets in Settings › Secrets. Nobody can view a value after it’s saved: the apps see only names, who changed them and when.
  • Each value is encrypted with AES-256-GCM, using a fresh IV and the repo and name as additional data, under a key derived with HKDF-SHA256 from SECRETS_KEY. SECRETS_KEY is a Worker secret if you set one; otherwise the factory generates a random key and stores it in D1. In that case, anyone who can read the D1 database can read the key too.
  • The factory sends a repo’s values only to the machine running a task on that repo, and only while the task is being planned, built or reviewed. The only other way to get values is maple-runner secrets pull, which works only on a machine whose owner is an org admin.
  • Every secret change and every time values are sent to a machine is recorded in the audit log, with names only.

GitHub App and its tokens

  • The app asks for: contents (write), pull requests (write), checks (write), actions (write), commit statuses (read), metadata (read), and organization members (read) for an org factory.
  • The factory never gives out the app’s full access. For each job it mints an installation token for one repository, with only that job’s permissions, which expires after an hour. A runner fetching code gets contents: read. A runner pushing a branch gets contents: write.
  • A runner only gets a token for the repo of a task that is assigned to that machine.
  • The app is public on GitHub, so that it can be installed on repos in other accounts. The factory only uses installations on your organization and on accounts an admin approved.
  • The app’s webhooks are checked against GITHUB_WEBHOOK_SECRET (HMAC-SHA256), and Linear’s against its signing secret.

Audit log

The D1 audit table records who did what and when: sign-ins and refused sign-ins, admin grants, machines enrolled and removed, sessions opened and killed, repos, secrets, worktree scripts, policy, prompts and connectors changed, secrets sent to a machine, and tasks created, moved, merged and cancelled. Secret values and script contents are never written to it. There’s no audit viewer in the apps yet: you read the table with wrangler d1 execute.

Local development routes

/dev/* routes, and signing in without GitHub, only work when the DEV_LOGIN variable is set and the request’s host is localhost or 127.0.0.1. Otherwise they return 404. DEV_LOGIN is meant for .dev.vars and isn’t part of a deployed factory’s configuration.

Runner maple-runner

Network

  • The runner makes one outbound WebSocket connection to your factory (wss://<factory>/runner/connect), authenticated with its machine token. It doesn’t open any port for inbound connections. Ports it uses for its own work bind to 127.0.0.1.
  • It uses TLS (rustls) for that connection and for downloading updates.
  • Release builds also send error reports to Sentry, and read the factory’s /healthz to tag them with its organization. MAPLE_TELEMETRY=off stops both.

Where it runs, and what it can reach

  • The runner is installed per user, as a launchd agent on macOS or a systemd user service on Linux, and runs as that user. It doesn’t use root.
  • Coding agents (Claude Code, Codex) run as that same user, with the same access to files, credentials and network that user has. Treat a runner machine as one where agents can do anything that user account can do.
  • Factory sessions start Claude Code in its auto permission mode, with git, the repo’s configured commands and the factory’s own MCP tools pre-approved. They start Codex in its workspace-write sandbox with network access and automatic review of approvals.
  • Sessions run in tmux, on a private tmux server whose socket is in ~/.config/maple/. Each task gets its own git worktree, outside the repo, on its own agent/… branch.
  • The folder browser and file views in the apps only show paths under the user’s home directory. Paths containing .. are refused.
  • The machine token is saved in ~/.config/maple/runner.json, readable only by that user (mode 0600).

Secrets on the machine

  • A task’s secrets reach its session through a one-time file (mode 0600, in ~/.config/maple/secrets/, never in the worktree). The pane’s shell reads it and deletes it before starting the agent. The values are in the pane’s processes only, not in tmux’s session environment.
  • The agent working on a task can read that repo’s secrets. Before the runner sends output to the factory (logs, proofs, the terminal stream and its replays), it replaces each secret value with ***. Values shorter than 6 characters aren’t replaced, and neither are encoded forms of a value, such as base64.
  • maple-runner secrets pull writes to a .env.local with mode 0600, and refuses if that file isn’t gitignored. The runner also refuses a pull that comes from a process inside one of its sessions. That check can be bypassed by a process that detaches itself. What actually stops an agent on a member’s machine is the factory’s check that only an admin’s machine can pull.
  • Other processes running as the same user can read a process’s environment.

Pushing to GitHub

The runner pushes a task’s branch with a one-hour token for that repo only. The token is passed as an argument to that one git command, and is never written to git config, a remote, or a log. An empty credential.helper stops a keychain helper from saving it. Pushing with the machine’s own git credentials is a setting that is off unless someone turns it on.

Installs and updates

  • Runner releases are described by a manifest that is signed with an Ed25519 key. The public key is compiled into the runner. A runner checks the signature before it trusts anything in the manifest, then checks that the download matches the manifest’s size and SHA-256. It only installs a version newer than the one it’s running.
  • Runners download releases through your factory, which passes along maplefactory.dev’s feed. Because of the signature check, someone who controlled the factory or the feed could hold back updates, but couldn’t make runners install a build of their own.
  • macOS runner builds in the feed are code-signed with a Developer ID, with the hardened runtime.
  • The first install from /install.sh is a shell script. It checks the binary against the manifest’s SHA-256 but doesn’t check the manifest’s signature, so it relies on HTTPS to your factory. Every update after that is checked against the signature.

Mac app

  • Signing. Release builds are signed with a Developer ID Application certificate, with the hardened runtime and a secure timestamp. This covers the app, its bundled runner and tmux, and Sparkle’s helpers. The release script refuses to ship a build that isn’t signed with a Developer ID. The app and the DMG are each notarized by Apple and stapled.
  • Updates. The app updates with Sparkle from https://updates.maplefactory.dev/appcast.xml and checks hourly. Each update is signed with an EdDSA (Ed25519) key, and Sparkle checks the signature against the public key built into the app before it installs.
  • Credentials. Your factory token is stored in the macOS login Keychain, one item per factory address. The exception is a plain-http:// local development factory, whose token is kept in the app’s preferences.
  • Connections. The app connects to your factory over HTTPS and WebSockets, to updates.maplefactory.dev for updates, to GitHub for avatars, and to Sentry with crash and error reports unless you turn them off. GitHub sign-in opens github.com in your browser.

Error reports

The server, web app, runner and Mac app report errors and crashes to Maple Factory’s own Sentry projects, hosted by Sentry in the US. This is on by default in every factory, including ones you deploy yourself, so problems can be found and fixed. Each part can be turned off, and the server can report to your own Sentry instead.

What’s sent

  • An error’s message and stack trace, and crashes and panics.
  • The component and its version (for example maple-server@0.56.0 or maple-mac@0.2.1), the operating system, and your factory’s GitHub organization login as a tag.
  • The Mac app’s events carry Sentry’s anonymous install ID.
  • The web app loads Sentry’s browser SDK from browser.sentry-cdn.com, pinned to one version with a Subresource Integrity hash.
  • Error messages are sent as written. Some can name a repo, a branch, a file path or a command that failed.

What’s never sent

  • Code, diffs, prompts, terminal output, tokens, secrets or cookies.
  • Request bodies, query strings or Authorization headers. The server and web app remove these from every event before it leaves, along with webhook signature headers.
  • Who is signed in, or the machine’s hostname. The runner also replaces your home folder with ~ in paths.
  • The runner sends only error-level logs and panics. The web and Mac apps send no console, click or network breadcrumbs, and the Mac app sends no screenshots or window contents.
  • The SDKs tell Sentry not to take a user’s IP address from the connection.

Turning it off

  • Server: a factory admin turns off Send error reports to Maple Factory in the web app’s Settings › General. Or set the Worker variable or secret SENTRY_DSN to off, or to your own Sentry DSN to report there instead; a SENTRY_DSN set on the Worker wins over the toggle, which then shows it’s locked.
  • Web app: follows the server. It sends nothing when the server’s reports are off.
  • Runner: set MAPLE_TELEMETRY=off in its environment, including its launchd or systemd service.
  • Mac app: turn off Send crash and error reports in Settings › General › Privacy. It takes effect straight away. Or run defaults write dev.maplefactory.app MapleTelemetry off, or set MAPLE_TELEMETRY=off.
  • Builds you make yourself (debug builds of the runner and Mac app) never report.

Reporting a vulnerability

Email andrea.fomera@gmail.com. Please report privately, and don’t disclose the issue publicly until a fix has shipped. Include:

  • the affected component (server, runner or Mac app) and its version. The server’s version is at /healthz, and the runner’s is shown by maple-runner --version;
  • steps to reproduce;
  • what an attacker could do with it.

This is also published as /.well-known/security.txt.
